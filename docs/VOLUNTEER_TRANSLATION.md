# 翻訳ワーカーのプールとボランティア枠 仕様 (v1)

翻訳エンジンを複数束ねる「プール」と、第三者が計算を提供する「ボランティア枠」の仕様。
直結プールと匿名の層のサーバーAPI（17.1 の第1・第2段階）は実装済み。ワーカー、検査、参加・同意・匿名ログインの画面は未実装。現行の API と動作は [SPEC](SPEC.md) が正で、実装した範囲は SPEC に反映する (19 章)。
このファイルだけを読めば実装を始められるように書く。

不特定の人の間で原文と訳をやり取りするので、3 章の脅威と対策を先に読むこと。
数値のうち「暫定」と書いたものは、モックと実測で決め直す。設計の判断と理由は 18 章にまとめる。

## 1. 目的と範囲

### やること

- 閉域内の複数の翻訳エンジンを 1 つのサーバーで束ねる (直結プール)
- 公式のボランティア枠: 参加者の端末のエンジンで訳す。利用者は登録なしでも使える
- デスクトップアプリから計算を提供できるようにする
- 参加者が原文を読める前提で、渡す内容を絞り、割り当てを分散し、改ざんを検出する

### やらないこと (v1)

- 利用者と参加者の間の暗号化。仲介は原文と訳を読める (18 章の決定 3)
- 参加者の端末での秘匿実行 (TEE など)。参加者は自分の端末で処理する内容を読める。一般の PC と GPU には、
  持ち主から推論の中身を隠す仕組みが無い
- 利用者と参加者の直接の通信。互いの IP アドレスは相手に見せない
- 計算の提供量に応じた優先 (18 章の決定 8)
- サーバー側での訳の保存と使い回し。別の利用者に訳が渡る経路を作らない
- 招待コードによる参加の制限
- 資格の発行での計算の課題 (proof of work)
- 日本の外への提供。利用者も参加者も日本の中に限る (13 章)
- 利用者からの誤訳の報告の受け付け。ジョブとワーカーの対応を残さないため
- 仲介での利用者の情報の保存。匿名の利用者について、仲介は永続の記録を持たない (12 章)

## 2. 用語と構成

| 用語 | 意味 |
| --- | --- |
| 仲介 | `server/translator.py`。認証、入力検証、待ち行列、割り当て、訳の中継、改ざんの検出を行う |
| プール | 1 つの仲介が訳の処理を渡す先の集まり。仲介 1 つにつきプール 1 つ |
| 直結プール | 運営が管理するエンジンに、仲介から閉域内で直接つなぐ。既定は1エンジン・4枠の直結プール |
| ボランティア枠 | 参加者の端末のエンジンに訳させるプール。原文は参加者の端末に渡る |
| ジョブ | 1 区切りの翻訳 (`POST /api/translate` 1 回) |
| ワーカー | ボランティア枠で訳す端末 1 台。1 台が 1 枠を提供する |
| エージェント | 参加者の端末で動き、仲介から受けたジョブを localhost のエンジンに渡すプロセス |
| 所有者 | ワーカーを登録したアカウント。同じ所有者のワーカーは 1 人として数える |
| 層 | 利用者の区別。登録済み (OIDC のアカウント) と匿名 (登録なし) |
| 確認用ジョブ | 仲介が作る合成のジョブ。基準の訳と比べて異常なワーカーを見つける |

```text
利用者 (Web / デスクトップ / 拡張)
   │ HTTPS: POST /api/translate (SSE)
   ▼
CDN → 前段 (nginx、oauth2-proxy) → 仲介 ──→ 運営のエンジン (直結プール。ボランティア枠では検証専用)
                                    ▲
                                    │ HTTPS: 外向きの接続だけ (ロングポーリング、結果の POST)
                                エージェント → localhost のエンジン (参加者の端末)
```

プールの種類は仲介の起動時に `TR_POOL_KIND` で決める。運営管理枠とボランティア枠は別の仲介 (別のオリジン) にする。
1 つの仲介が両方の利用者のジョブを扱うことはない。混雑や停止による切り替えは同じプールの中に限る。
クライアントは既存の規則どおり、認証情報と訳のキャッシュを接続先ごとに分ける (SPEC 6.3)。

## 3. 信頼の境界と脅威

### 3.1 誰が何を読めるか (ボランティア枠)

| 相手 | 原文・文脈・用語集・前の訳・訳 | 利用者の資格・IP | ワーカーの資格・IP |
| --- | --- | --- | --- |
| CDN と前段 | 読める | 読める | 読める |
| 仲介 (運営) | 読める (メモリの上だけ。残さない) | 読める | 読める |
| 運営のエンジン | 抜き取ったジョブだけ読める | 読めない | 読めない |
| 割り当てられたワーカー | そのジョブの分を読める | 読めない | 自分の分だけ |
| ほかのワーカー、ほかの利用者 | 読めない | 読めない | 読めない |

### 3.2 前提

- ワーカーを信頼しない。原文を記録する、訳を改ざんする、別のモデルで訳す、答えない、のどれも起こると考える
- 利用者を信頼しない。大量に送る、資格を取り直す、参加者の端末を攻撃する入力を送る、のどれも起こると考える
- 仲介は運営が管理するが、エージェントは仲介も信頼しすぎない。仲介が侵害されても、参加者の端末で
  翻訳以外のことをさせられない作りにする (11 章)
- ワーカーが読むこと自体は技術では防げない。防げるのは、渡す量、渡す相手の偏り、改ざんの見逃しだけ

### 3.3 脅威と対策

| # | 脅威 | 対策 | 章 |
| --- | --- | --- | --- |
| T1 | ワーカーが原文を記録・公開する | 利用前の同意。利用者の識別子を渡さない。区切りごとに別の所有者へ分散。所有者ごとの比率の上限。参加はアカウント登録と規約同意 | 4、7、8 |
| T2 | 1 人が多数の端末を登録し、分散した断片を集め直す | 所有者ごとの端末数の上限。同じ所有者・同じネットワークを 1 人と数える | 7、8 |
| T3 | ワーカーが訳を改ざんする (URL の差し替え、誤訳、不快な文) | 確認用ジョブ、抜き取りの再実行、形式の検査、検疫。訳は文字列としてだけ表示する | 9、10 |
| T4 | ワーカーが別のモデルや壊れたエンジンで訳す | 確認用ジョブと抜き取り。申告は信用しない | 10 |
| T5 | ワーカーが特定の利用者や文書を狙う | 割り当ては無作為。ワーカーはジョブを選べず、誰のジョブかも分からない | 7 |
| T6 | ワーカーが答えない、遅く返す、枠だけ取る | 期限 (最初の断片、断片の間、全体)。失敗の率で検疫 | 9 |
| T7 | ワーカーが大きな結果や壊れた結果を送る | 断片と全体の長さの上限、連番の検査、制御文字の除去 | 9 |
| T8 | 失効したワーカー、他人の割り当てに結果を送る | 割り当て ID をワーカーの資格にひも付ける。失効後と期限後の結果は捨てる | 8、9 |
| T9 | 利用者が大量に送って枠を埋める | 層ごとの上限、全体の待ち行列の上限、IP 単位の短時間の制限、CDN | 5、7、13 |
| T10 | 匿名の資格を取り直して上限をすり抜ける | 匿名の層の制限を資格に頼らない (層全体の枠、IP 単位、発行の制限) | 5、7 |
| T11 | 利用者が参加者の端末を攻撃する入力を送る | 仲介で検証し、エージェントでも検証し直す。エージェントは構造化した入力からプロンプトを自分で組む | 6、11 |
| T12 | 仲介が侵害され、参加者の端末に任意の処理をさせる | エージェントは翻訳の入力だけを受け、上限を自分で持ち、コードや接続先を仲介から受け取らない | 11 |
| T13 | 前段の設定の誤りで利用者名や IP を偽れる | 前段が利用者名のヘッダーを消す。IP のヘッダーは前段からの接続でだけ読む | 13 |
| T14 | Web の画面への別サイトからの要求 (CSRF)、訳に混ぜたスクリプト | `SameSite=Strict` の Cookie、`Origin` の確認、JSON だけ受ける。訳は `textContent` で表示 | 5、6 |
| T15 | ログや永続の保存から内容や資格が漏れる | 原文・訳・資格をログに書かない。ワーカーの資格はハッシュで持ち、匿名の資格は保存しない | 12 |
| T16 | 運営管理枠を選んだ利用者のジョブがボランティアへ流れる | 仲介 1 つにプール 1 つ。同意の無い要求はボランティア枠の仲介が断る | 2、6 |

### 3.4 残る危険 (受け入れる)

- ワーカーは渡された区切りを読める。`history` を付けるので、実際には 2 区切り分 (最大で原文 8,000 文字と訳) を読める。
  `context` と用語集は、そのジョブを受けた全員が読める
- 分散しても、漏れる量の期待値は悪意のある所有者の割合と同じ。分散が変えるのは「1 人に全部」を「多くの人に断片」にすることだけ
- 所有者が少ない間は、比率の上限が成り立たない (7.3)。少数の人が多くを読める。この間もページ翻訳を受ける
- アカウントの登録に要るのはメールアドレスだけなので、1 人が複数のアカウントを作れる。所有者ごとの上限 (T2) は、
  手間を増やすだけで防ぎ切れない。IP のまとまりと比率の上限で補う
- 仲介は利用者とジョブの記録を持たないので、乱用や漏えいを後から調べる手がかりがほとんど無い
- 改ざんの検出は確率的で、見つかるのは配信の後。1 区切りの改ざんは利用者に届き得る
- CDN の事業者は内容と資格を読める立場にある
- 参加者の端末のメモリやスワップに残る内容は、エージェントからは消し切れない

これらは同意の画面 (4 章) に書く。

## 4. 利用者への説明と同意

ボランティア枠は初期状態で無効。クライアントは、利用者が接続先として選び、次の同意を済ませるまで、
ボランティア枠の仲介へ原文を送らない。

### 4.1 同意の画面

接続先を初めて選んだときに、最初の送信より前に出す。次を具体的に書く。

- 原文、文脈、用語集、直前の区切りの原文と訳が、運営以外の参加者の端末で処理され、その参加者が読める
- ページ翻訳では、開いているページの本文 (ログイン後の画面を含む) が送られる
- 参加者は記録しない旨の規約に同意しているが、技術的に防ぐ手段は無い
- 訳が改ざんされる可能性があり、検出は完全ではない
- 運営と CDN の事業者も内容を読める立場にある。検査のため、一部を運営のエンジンで訳し直す
- 他人の個人情報、業務上の秘密、認証に使う情報を入れない。そうした文はローカルモードか運営管理枠で訳す

同意には版 (`consent_version`、整数) を付ける。渡す内容や相手が変わったら版を上げ、同意を取り直す。
同意は端末の設定に接続先ごとに保存する。サーバーには保存しない。

### 4.2 クライアントが守ること

- ボランティア枠へ送っている間は、送信先がボランティア枠であることを画面に出し続ける (翻訳ポップアップ、
  メインウィンドウ、拡張のポップアップとページ上の表示)
- 拡張は、入力欄 (`input`、`textarea`、`select`) と編集できる領域 (`contenteditable`) の値を
  ボランティア枠へ送らない。シークレットウィンドウではボランティア枠を使わない
- ページ翻訳は、利用者がそのタブで翻訳を始めたときだけ送る (現行と同じ)。自動で始めない
- 訳は文字列として扱う。HTML として解釈しない。訳の中の URL をリンクにしない
- 同意していない接続先へ、設定の移行や自動の切り替えで送らない

## 5. 利用者の認証と層

### 5.1 層

| 層 | 認証 | 使える機能 | 優先 |
| --- | --- | --- | --- |
| 登録済み | 既存の OIDC (SPEC 6 章)。前段が `X-Forwarded-User` を付ける | すべて | 高い |
| 匿名 | 仲介が発行する匿名の資格 | すべて | 低い (7.2) |

匿名の層は `TR_ANON_ENABLED=1` のときだけ有効。既定は無効で、個人の運用は今までどおり OIDC か閉域の認証だけで動く。
仲介は、`X-Forwarded-User` があれば登録済み、無くて匿名の資格があれば匿名として扱う。
登録済みのアカウントは、確認の済んだメールアドレスだけで作れる。使い捨てのメールアドレスのドメインは IdP で断る。氏名や住所は受け取らない。メールアドレスを持つのは
IdP だけで、仲介には渡さない (scope に `email` を入れない。SPEC 6.1)。仲介に渡る利用者名は、メールアドレスから
作らない名前にする。

### 5.2 匿名の資格

氏名もメールアドレスも受け取らない。仲介は匿名の資格を保存しない。資格は仲介の鍵で署名した値で、
仲介は署名と期限を確かめるだけにする。

| 項目 | 規則 |
| --- | --- |
| 形式 | `pta_<128 bit の乱数>.<期限>.<HMAC-SHA256>`。鍵は `TR_TOKEN_KEY` |
| 有効期限 | 発行から 30 日 (暫定)。切れたら、または 401 を受けたら取り直す |
| 仲介が保存するもの | なし。乱数の部分は、メモリの上のカウンターの鍵にだけ使う |
| 失効 | 資格の単位ではできない。`TR_TOKEN_KEY` を替えると、すべての資格が無効になる |

資格を 1 つずつ失効できないのは、取り直せる資格を失効しても意味が薄いから。乱用は 5.3 と 7.2 の制限で抑える。

- デスクトップは資格を OS の資格情報の保管に、拡張は `chrome.storage.local` (`sync` は使わない) に置き、
  API には `Authorization: Bearer` で付ける
- Web の画面は Cookie を使う。名前は `__Host-pta`、属性は `HttpOnly; Secure; SameSite=Strict; Path=/`。
  スクリプトから資格を読めないようにする
- 資格は接続先ごとに分け、別の接続先へ送らない (SPEC 6.3 と同じ)

### 5.3 発行の制限

匿名の資格は取り直せるので、資格の単位の制限だけでは乱用を止められない。次を重ねる。

- 発行は IP アドレス (IPv4 は /24、IPv6 は /48 にまとめる) ごとに 1 時間 5 個まで (暫定)。
  数えるのはメモリの上だけで、IP をディスクにもログにも書かない
- サービス全体の発行数に 1 分あたりの上限 (`TR_ANON_ISSUE_PER_MINUTE`、既定100) を置く。超えたら 503 と `Retry-After`
- CDN でも、発行の API に IP 単位の制限をかける (13 章)
- 匿名の層の実行は、資格ごとの上限に加えて、同じ IP のまとまりごとの同時実行数と、層全体の枠 (7.2) で縛る
- それでも足りないときは匿名の層を止められる (`TR_ANON_ENABLED=0` で再起動)。登録済みの層は影響を受けない

### 5.4 層ごとの上限 (暫定)

| 項目 | 登録済み | 匿名 |
| --- | ---: | ---: |
| 同時に流せる数 (`max_in_flight`) | 2 | 1 |
| 同じ IP のまとまりの同時実行 | なし | 4 |
| 1 時間に送れる原文 (文字) | 600,000 | 100,000 |
| 待ち行列に置ける数 | 利用者ごとに 8 | 資格ごとに 4 |

入力の規則 (原文 4,000 文字、プロンプト全体 12,000 文字など) は両方の層で同じ。API を層で変えない。

## 6. 利用者向け API の変更

既存の `GET /api/config` と `POST /api/translate` を広げる。足した項目を送らない古いクライアントは、
直結プールでは今までどおり動く。ボランティア枠では同意の項目が無いので断られる (意図した動き)。

### 6.1 `GET /api/config` に足す項目

```json
{
  "pool": { "kind": "volunteer", "consent_version": 1 },
  "tier": "anonymous",
  "concurrency": { "max_in_flight": 1, "scope": "user" }
}
```

`pool.kind` は `direct` か `volunteer`。`volunteer` のとき、クライアントは 4 章の同意を済ませてから送る。
匿名の層では `user` は空文字にする。

### 6.2 匿名の資格の API (匿名の層が有効なときだけ)

`POST /api/anonymous` で資格を発行する。本文は `{}`。応答は `{"credential": "pta_...", "expires_in": 2592000}`。
`Origin` が `TR_PUBLIC_SERVER_URL` と一致する要求はWeb用とし、Cookieを設定して本文に資格を入れない。
Originがない、または `chrome-extension://` で始まる場合は本文に資格を返し、Cookieを設定しない。
それ以外のOriginは403で断る。資格を捨てるときは、端末から消すだけでよい。

`Content-Type: application/json` を必須にする。Cookie認証は `Origin` が仲介の公開URLと一致する場合に通す。
Originがない場合は `Sec-Fetch-Site: same-origin` かつGETまたはHEADの場合だけ通す。
`same-site`・`cross-site`・ヘッダー欠落は403。POSTはOriginの一致を必須とし、Originがなければ403。
OPTIONSには対応せずCORSヘッダーも返さないため、ほかのWebサイトからJSONの要求をプリフライトで許可しない。

### 6.3 `POST /api/translate` に足す項目

| 項目 | 規則 |
| --- | --- |
| `purpose` | 任意。`"interactive"` (既定)、`"page_visible"`、`"page_rest"`。割り当ての順のヒント (7.2)。上限をゆるめる効果は無い |
| `group` | 任意。ページ翻訳 1 回ごとにクライアントが作る乱数 (22 文字以上の base64url)。URL やタイトルから作らない。仲介の中だけで使い、ワーカーに渡さない |
| `consent` | ボランティア枠では必須。クライアントが取った同意の版。無いか古ければ 403 (`{"error": "...", "code": "consent_required"}`) |

応答は今までと同じ SSE。受け付けてから割り当てまでの間は `: ping` を送る。足す動きは次のとおり。

| 状況 | 応答 |
| --- | --- |
| 日本の外からの要求 (13 章) | 403。`code` は `region` |
| 層や利用者の上限を超えた | 429 (今までと同じ) |
| 待ち行列が一杯 | 503 と `Retry-After`。`code` は `busy` |
| 待ちが期限 (`TR_QUEUE_TIMEOUT`、暫定 120 秒) を超えた | SSE の `{"error": "...", "code": "queue_timeout"}` |
| ワーカーが途中で失敗した | 最初の断片の前なら 1 度だけ割り当て直す (7.4)。それ以外は SSE の `{"error": "...", "code": "worker_failed"}` |

利用者が接続を閉じたら、待っているジョブは待ち行列から外し、実行中なら割り当てを取り消す (9.4)。
終了の通知 (`done`) の無いまま上流が切れたときは、成功として扱わない。

## 7. 待ち行列と割り当て

### 7.1 枠

直結プールの枠は、エンジンごとに設定した数 (`TR_UPSTREAMS`)。ボランティア枠は、空きを申告して待っている
ワーカー 1 台が 1 枠。ジョブは枠が空くまで仲介の待ち行列で待つ。

### 7.2 順番

1. 用途の順: `interactive`、`page_visible`、`page_rest`。下の用途が待ち続けないよう、待ち時間が
   `TR_AGING_SECONDS` (暫定 30 秒) を超えたジョブは 1 つ上の用途として扱う。引き上げは1段だけで、
   `page_rest` は61秒待っても `page_visible` として扱い、新しい `interactive` より後になる
2. 同じ用途の中では、層に重みを付けて順に取る。登録済み 4 に対して匿名 1 (暫定)。匿名を完全に後回しにはしない
3. 同じ層の中では、利用者 (匿名は資格) を順番に回す。1 人が続けて取らない
4. 匿名の層が同時に使える枠は、全体の `TR_ANON_SHARE` (暫定 0.5) まで。登録済みの待ちが無い間は、空いている枠を使ってよい。
   枠数は `max(1, floor(全枠 × TR_ANON_SHARE))` とし、1枠のプールでも匿名を進める。
   既に実行中の匿名要求は中断しない。同じIPのまとまりでは4本まで実行し、超える分は待たせる
5. ページ翻訳 (`page_visible`、`page_rest`) は、利用者ごとに同時に 1 本までにする。複数のタブの合計で数える。
   ページ要求の未完了数（待機中と実行中）の受け付け上限は `max(1, TR_MAX_ACTIVE_PER_USER - 1)`。
   これを超えるページ要求は429で断り、対話のための余地を残す。対話要求も含む全用途の未完了数には
   `TR_MAX_ACTIVE_PER_USER` を適用する。未完了数は上流の終了処理後に減らし、受け付け失敗時にも枠を残さない。
   枠が 1 つのプールでは、実行中の区切りが終わってから `interactive` に枠を渡す

`purpose` はクライアントの申告なので、上限をゆるめる根拠にしない。偽って `interactive` と申告しても、
利用者ごとの同時実行数と 1 時間の文字数で頭打ちになる。

### 7.3 分散 (ボランティア枠)

1 人の参加者に内容が集まらないよう、区切りごとに渡す相手を変える。

1. 空いていて検疫されていないワーカーの中から、無作為に選ぶ。先に待っていた順や速さの順にしない
2. 同じ利用者の直前のジョブ、同じ `group` の直前の `TR_SPREAD_WINDOW` (暫定 8) 個のジョブを受けた所有者は、
   ほかに候補があれば避ける。候補が無ければ待たせずに渡す
3. 1 人の所有者に渡す割合は、直近 10 分のジョブの `TR_OWNER_SHARE_MAX` (暫定 0.2) までにする。
   動いている所有者が 5 人に満たない間は成り立たないので、上限を「1 ÷ 所有者の数」の 1.5 倍に読み替える。
   この間もページ翻訳を含めて受ける (18 章の決定 13)。その状態であることを運営に見える形で記録する (集計の `spread=degraded`)
4. 同じ所有者のワーカーと、同じ IP のまとまり (IPv4 は /24、IPv6 は /48) からつないでいるワーカーは、
   2 と 3 で 1 人の所有者として数える

ワーカーに渡すのは、訳すための入力 (9.2) だけにする。次は渡さない。

- 利用者の名前、資格、層、IP アドレス、クライアントの種類
- `group`、`purpose`、同じ文書の中の位置、残りの区切りの数
- ほかのジョブやほかのワーカーの情報、待ち行列の状態

`history` は付ける (18 章の決定 6)。各ワーカーは、渡された区切りと直前の区切りの 2 つ分を読める。

### 7.4 割り当て直し

ワーカーが期限を過ぎた、切れた、エラーを返したとき、利用者に最初の断片を送る前なら、同じプールの別の所有者の
ワーカーへ 1 度だけ割り当て直す。断片を 1 つでも送った後と、2 度目の失敗は、SSE のエラーで終える。
割り当て直すと、同じ区切りを 2 人が読むことになる。同意の画面の「参加者」は複数であると書いておく。

## 8. ワーカーの登録と資格

### 8.1 参加の条件

- OIDC のアカウントでログインしていること (利用者の登録済みの層と同じ IdP。メールアドレスだけで作れる)
- 日本の中からつないでいること。ポーリングのたびに確かめ、外からのワーカーにはジョブを渡さない (13 章)
- 参加の規約に同意していること。規約には、処理した内容を記録しない、目的の外に使わない、公式のエージェントを
  改変して内容を取り出さない、、日本の中で
  参加する、を入れる。同意した版と日 (日の単位) を所有者ごとに保存する
- 1 人の所有者が登録できる端末は `TR_WORKERS_PER_OWNER` (暫定 2) 台まで

### 8.2 登録と資格

| API | 認証 | 動き |
| --- | --- | --- |
| `POST /api/worker/register` | OIDC (`X-Forwarded-User`) | 本文は `{"terms_version": 1}`。応答は `{"worker_id": "...", "secret": "ptw_...", "expires_in": 604800}`。秘密は 1 度だけ返す |
| `POST /api/worker/renew` | OIDC と、本文の `worker_id` | ワーカーの資格の期限を 7 日延ばす。アカウントが無効になれば延ばせず、資格は期限で切れる |
| `DELETE /api/worker/<worker_id>` | OIDC (所有者本人) | 登録を解除し、資格を失効させる |
| `GET /api/worker/mine` | OIDC | 自分のワーカーの一覧と状態 (待機、検疫、失効) |

- 秘密は 256 bit の乱数。サーバーは SHA-256 のハッシュ、所有者、期限、状態だけを持つ。端末は OS の資格情報の保管に置く
- 所有者が登録を解除したら、そのワーカーの記録をすぐ消す。運営が失効した所有者は、登録し直しを断るために名前と失効の状態だけを残す
- ワーカーの資格は利用者の資格と別のもの。ワーカーの資格で `POST /api/translate` は呼べず、利用者の資格で
  ワーカーの API (9 章) は呼べない
- 運営は、ワーカー 1 台、または所有者のすべてのワーカーを失効できる。失効は次のポーリングと結果の POST から効く

### 8.3 試用

登録した直後のワーカーには、確認用ジョブだけを渡す。`TR_PROBATION_JOBS` (暫定 20) 個を続けて合格したら、
利用者のジョブを渡し始める。検疫から戻るときも同じ。ワーカーからは、確認用ジョブと利用者のジョブを区別できない。

## 9. ワーカーのプロトコル

エージェントが仲介へ外向きの HTTPS でつなぐ。参加者の端末で待ち受けはしない。認証は
`Authorization: Bearer ptw_...`。本文は JSON。接続は使い回す。

### 9.1 `POST /api/worker/poll`

空きがあるときに呼ぶ。本文は `{"agent_version": "0.5.0", "model": "<モデルのファイルの SHA-256>"}`。
仲介はジョブが入るまで最大 25 秒待ち、無ければ 204 を返す。1 台のワーカーが同時に開けるポーリングは 1 本。

仲介は、`agent_version` が `TR_MIN_AGENT_VERSION` より古いワーカーと、`model` が仲介の認めるものと違うワーカーに
ジョブを渡さない (403 と理由)。どちらも申告なので、信用の根拠にはしない (T4 は 10 章で見る)。

### 9.2 割り当て

```json
{
  "assignment_id": "<128 bit の乱数>",
  "deadline_seconds": 120,
  "input": {
    "text": "...",
    "target_lang": "en",
    "source_lang": null,
    "form": null,
    "context": "",
    "glossary": [{ "source": "...", "target": "..." }],
    "history": [{ "source": "...", "target": "..." }]
  }
}
```

`input` は SPEC 5.2 の要求と同じ形で、仲介が検証を済ませたもの。プロンプトの文字列は渡さない。
エージェントが PFML3 を自分で組む (11 章)。`assignment_id` はそのワーカーの資格にひも付き、ほかのワーカーは使えない。

### 9.3 `POST /api/worker/result`

```json
{ "assignment_id": "...", "seq": 0, "text": "訳の断片", "done": false }
```

- `seq` は 0 から 1 ずつ増やす。仲介は、既に受けた `seq` を捨て (再送で二重に表示しない)、飛んだ `seq` はエラーにする
- 最初の断片、最後の断片、終了の通知はすぐ送る。途中の断片は 200 ms を目安にまとめて送る
- 終わりは `{"assignment_id": "...", "seq": n, "done": true, "finish": "stop"}` (`finish` は `stop` か `length`)。
  失敗は `{"assignment_id": "...", "seq": n, "error": "engine"}`。エラーの本文に原文や上流の応答を入れない
- 応答は `{"stop": false}`。`true` なら、エージェントはエンジンへの接続を閉じて生成を止める

仲介は、結果を利用者に送る前に次を確かめる。外れたらその割り当てを失敗にする。

| 検査 | 規則 |
| --- | --- |
| 資格と割り当て | 資格が有効で、`assignment_id` がその資格のもので、期限の内で、まだ終わっていない |
| 大きさ | 1 回の POST の本文は 64 KB まで。訳の合計は、原文の長さから決まる `max_tokens` (`translator.py` の `max_tokens`) の 6 倍の文字数まで (暫定) |
| 期限 | 最初の断片まで 20 秒、断片の間 20 秒、全体で `deadline_seconds` (どれも暫定) |
| 文字 | `<|plamo:` を含む断片は受けない。改行とタブ以外の制御文字、双方向の上書きの文字 (U+202A〜U+202E、U+2066〜U+2069) は取り除く |

失効の後や期限の後に届いた結果は、内容を見ずに捨てる。

### 9.4 `POST /api/worker/ping`

実行中の割り当てがある間、5 秒ごとに呼ぶ。本文は `{"active": ["<assignment_id>"]}`、応答は
`{"stop": ["<assignment_id>"]}`。利用者が接続を閉じた割り当てを、結果の POST を待たずに止めるために使う。
止める通知が届くまでの目標は 5 秒以内 (暫定)。

## 10. 改ざんの検出

確認用ジョブと、利用者のジョブの抜き取りの再実行を組み合わせる。どちらも運営のエンジン (`TR_AUDIT_UPSTREAMS`) を
基準にする。運営のエンジンを設定していないボランティア枠は起動させない。

### 10.1 確認用ジョブ

- 原文は運営が用意する文の集まり (`TR_CANARY_FILE`) から取る。このリポジトリは公開なので、文の集まりを
  リポジトリにも配布物にも入れない。十分に大きくし、同じ文を同じ所有者に 2 度出さない
- 長さ、言語の組、`history` や用語集の有無を、利用者のジョブの分布に寄せる。ワーカーから見分けられないようにする
- 基準の訳は、出す直前に運営のエンジンで作る
- 頻度は、ワーカーごとに処理したジョブの `TR_CANARY_RATE` (暫定 0.05)。試用の間は全部

### 10.2 抜き取りの再実行

- 利用者のジョブの `TR_AUDIT_RATE` (暫定 0.02) を、配信が終わった後に運営のエンジンで訳し直し、ワーカーの訳と比べる
- どのジョブを抜き取るかは仲介の乱数で決め、ワーカーにも利用者にも知らせない
- 抜き取ったジョブの入力と訳は、比べ終わるまでメモリの上にだけ置く。ディスクにもログにも書かない。
  待ちが `TR_AUDIT_BACKLOG` (暫定 50) 個を超えたら、新しい抜き取りをやめる (内容をためない)
- 検疫の候補になったワーカー (10.4) は、抜き取りの率を上げる

### 10.3 比べ方

同じモデルでも、エンジンの版、量子化、GPU の違いで訳は少し変わる ([訳の繰り返しと揺れの調査](REPEAT_INVESTIGATION.md))。
完全な一致は求めない。

- 似ている度合い: 文字の 2 つ組の重なり (Dice 係数)。しきい値は暫定 0.6。正しいワーカーどうしの分布を実測して決める
- URL とメールアドレス: 訳に出たものが、原文、用語集、基準の訳のどれかにあること。無ければ不合格
- 数字: 桁区切りと全角・半角をそろえたうえで、基準の訳に無い数字の列が訳にあれば不合格の候補にする
- 訳す先の言語: 訳の文字の種類が `target_lang` と合わなければ不合格

抜き取っていないジョブにも、原文と用語集だけでできる検査 (URL、長さ、文字の種類) は全部にかける。
こちらは配信の途中では止めず、ワーカーの成績にだけ数える。

### 10.4 成績と検疫

- ワーカーごと、所有者ごとに、合格と不合格の数、期限切れの数をメモリに持つ (内容は持たない)。保存はしない。
  仲介を再起動すると数は消え、検疫されていないワーカーも試用 (8.3) からやり直す。検疫と失効の状態だけは保存する
- 不合格が 1 度出たら、そのワーカーを検疫する。検疫の間は確認用ジョブだけを渡す。試用と同じ数を続けて合格すれば戻す
- 同じ所有者のワーカーで 24 時間に 3 度 (暫定) 不合格が出たら、その所有者のすべてのワーカーを検疫し、
  運営が失効するか戻すかを決める。自動では失効しない (誤検知で善意の参加者を締め出さない)
- 期限切れとエラーの率が高いワーカーは、割り当ての対象から一時的に外す

## 11. エージェント (参加者の端末)

デスクトップの設定に、初期状態でオフの「翻訳の処理を提供する」を置く。オンにする前に、参加の規約と
次の説明を出す: ほかの人の文がこの端末で処理される。内容は選べない。処理の間、GPU とメモリを使う。

### 11.1 プロセスと通信

- エージェントは、デスクトップの本体と別のプロセスにする。ファイルを読み書きする権限を、資格の読み取りのほかに持たせない
- 通信の相手は、設定された仲介 (HTTPS、証明書を検証する) と、localhost のエンジンだけ。待ち受けはしない
- 仲介から受け取るのは 9 章の JSON だけ。コード、設定、別の接続先、更新を、仲介から受け取らない。
  エージェントの更新は、アプリの署名付きの更新 (SPEC 7 章) だけで行う
- 翻訳の接続先と、計算の提供先は、別々に選べる

### 11.2 入力の扱い

仲介が侵害されても、参加者の端末で翻訳より広いことをさせないために、エージェントが自分で確かめる。

- 割り当ての `input` を、SPEC 5.2 と同じ上限でもう一度検証する (原文 4,000 文字、プロンプト全体 12,000 文字、
  用語集 200 件、`history` 4 組、`<|plamo:` を含まない、言語のコードが一覧にある)。上限はエージェントに埋め込み、
  仲介の指示で広げない
- PFML3 のプロンプトは、ローカル翻訳と同じ実装で組む (共通の[入力・期待値](../shared/local-translation-fixtures.json)で一致を確かめる)
- エンジンへは `temperature: 0`、`cache_prompt: false`、原文の長さから決めた `max_tokens` (上限 8,000) で投げる。
  これらを仲介から変えられない
- エンジンは、ローカル翻訳で取得して SHA-256 を検証したファイルだけを使う ([ローカル翻訳](LOCAL_TRANSLATION.md))

### 11.3 残さない

- 原文、訳、プロンプト、割り当て ID を、ファイル、ログ、エンジンの子プロセスのログに書かない。
  書くのは時刻、長さ、言語、状態だけ
- 提供したジョブの内容を、履歴、訳のキャッシュ、画面に出さない。参加者自身の翻訳と混ぜない
- ジョブが終わったら、入力と訳の文字列を捨てる。メモリやスワップに残る分までは消せない (3.4)

### 11.4 動きの制御

- アプリが起動している間に 1 枠を提供する。バッテリーで動いている間は、新しいジョブを受けない
- 自分の翻訳を優先する。自分の翻訳が始まったら、新しい割り当てを止め、実行中の区切りが終わってから枠を返す
- 1 つのジョブの実行時間を `deadline_seconds` で打ち切る
- 画面に、待機中・処理中・一時停止・検疫中と、処理した数を出す。「登録を解除」でワーカーの資格を失効させる (8.2)
- アプリの終了時は、実行中の割り当てにエラーを返してから終える

## 12. ログと保存

### 12.1 残さないもの

原文、文脈、用語集、`history`、訳、確認用ジョブの基準の訳、資格と token (ハッシュでないもの)、
上流とワーカーのエラーの本文。仲介、前段、CDN、エージェントのどのログにも出さない。

### 12.2 仲介が持つもの

仲介が持つ情報を最小にする。匿名の利用者については、永続の記録を何も持たない。

| 内容 | 場所 | 期間 |
| --- | --- | --- |
| 利用量のカウンター (層、利用者、匿名の資格の乱数、IP のまとまり) | メモリ | 1 時間 |
| ワーカーと所有者の成績 (数だけ) | メモリ | 再起動まで |
| 割り当て ID とワーカーの対応、抜き取りの入力と訳 | メモリ | そのジョブの検査が終わるまで |
| ワーカーの資格のハッシュ、所有者の名前、規約の版と同意の日、検疫と失効の状態 | 永続 | 登録の解除まで (失効した所有者は名前と状態だけ残す) |
| 集計 (1 分ごとの件数、層と用途ごとの待ち時間、エラーの数、`spread=degraded`) | ログ | 30 日 |

- ボランティア枠の仲介は、ジョブごとのログを書かない。集計だけを書く。利用者名、匿名の資格、ワーカーの ID、
  IP アドレスは、どのログにも出さない (直結プールは今までどおり、ジョブごとに利用者名と長さを書く)
- 利用者とワーカーの対応を残さない。誰のジョブをどのワーカーが処理したかは、検査が終わると分からなくなる
- 規約の同意の記録 (所有者の名前、版、日) は残す。参加者に記録の禁止を求める根拠になるので、最小の形で持つ
- メールアドレスは IdP だけが持つ。仲介は受け取らない
- 永続の保存は、標準ライブラリの `sqlite3` を使う。ファイルは仲介の利用者だけが読める権限 (0600) にする。
  `TR_TOKEN_KEY` はファイルか環境変数で渡し、コードとリポジトリに置かない

記録を持たないことの代償は、乱用や漏えいが起きたときに、後から調べられないこと。止める手段は、その場の制限
(5.3、7.2) と、ワーカーの検疫と失効 (10.4) だけになる。

## 13. 公開入口 (CDN と前段) の要件

本番の設定は非公開のリポジトリにある。ここには要件だけを書く。CDN は Cloudflare を想定する。

- Cookie認証では6.2のOriginとSec-Fetch-Siteの規則を使う。前段はこれらのヘッダーを保持し、
  OriginなしのGETを一律に断らない。OPTIONSの成功応答やCORSヘッダーを前段・CDNでも追加しない。
  拡張のOriginでの資格発行はCookieなしの応答にする。
- 文字数のカウンターは登録済みと匿名で分け、各10,000キーまでとする。匿名の容量超過で登録済みを断らない。
- 500のログにはメソッド・既知のルートのパス・例外の型だけを出す。クエリーは出さず、未知のパスは
  `<unknown>` とする。例外のメッセージとスタックトレースは出さない。
- 仲介は前段からしか届かない場所で待ち受ける。オリジンは CDN からの接続だけを受ける
- 前段は、クライアントが付けた `X-Forwarded-User` を必ず消す。OIDC を通した要求にだけ付け直す
- 匿名の API (`/api/anonymous`、匿名の資格を付けた `/api/config` と `/api/translate`) と、
  ワーカーの API (`/api/worker/poll`、`result`、`ping`) は、OIDC のプロキシを通さずに仲介へ渡す。
  `/api/worker/register`、`renew`、`mine`、`DELETE` は OIDC を通す
- クライアントの IP は、前段が付けるヘッダー (`TR_CLIENT_IP_HEADER`) からだけ読む。前段は、CDN が付けた値で
  このヘッダーを上書きし、クライアントが付けた値を通さない
- CDN と前段は、要求と応答の本文をログ、キャッシュ、検査用の保存に残さない。応答は `Cache-Control: private, no-store`。
  SSE をためない (バッファリングを切る)
- 提供は日本の中に限る。CDN で日本の外からの要求を断り、仲介も前段が付ける国のヘッダー (`TR_COUNTRY_HEADER`。
  Cloudflare では `CF-IPCountry`) が `TR_ALLOWED_COUNTRIES` (`JP`) に無い要求を 403 にする。利用者の API にも
  ワーカーの API にもかける。VPN などで国を偽ることは防げないので、規約にも書く
- クライアントの IP のヘッダーは、Cloudflare では `CF-Connecting-IP`。オリジンへの接続は、Cloudflare からのものだけに
  する (トンネルか、オリジン側での接続元の確認)
- CDN が持つログ (IP、時刻、パス) の項目と期間は Cloudflare の側で決まり、仲介からは消せない。
  プライバシーポリシーに書く
- CDN の事業者が内容を読める立場にあることを、同意の画面とプライバシーポリシーに書く
- HTTP/2 で、単文とページのストリームを並行して流せるようにする

Cloudflare の設定は次のとおりにする。項目の名前と、契約の種類で使えるかは、設定するときに確かめる。

| 項目 | 設定 |
| --- | --- |
| オリジンとの間 | 証明書を検証する暗号化 (Full (strict))。オリジンは Cloudflare からの接続だけを受ける |
| TLS | 1.2 以上。HTTP/2 を有効にする |
| 国 | 日本の外からの要求を、すべてのパスで断る |
| キャッシュ | `/api/` の下をキャッシュしない |
| IP 単位の制限 | `POST /api/anonymous` は 1 時間に 5 回、`POST /api/translate` は 1 分に 60 回 (どちらも暫定)。超えたら 429 |
| 本文の記録 | 要求と応答の本文を残す機能 (検査のための本文の記録、ログの外への転送) を使わない |
| ボットの対策 | ブラウザーでの確認を挟む機能を、`/api/` の下にかけない。デスクトップ、拡張、エージェントはブラウザーではないので通れなくなる |
| 応答の加工 | 本文を書き換える機能 (圧縮のし直し、スクリプトの差し込み) を `/api/` の下にかけない。SSE が届くのが遅れる |
- 開いたままの要求の数に、前段と仲介 (`TR_MAX_OPEN_REQUESTS`) の両方で上限を置く。`ThreadingHTTPServer` は
  開いた要求ごとにスレッドを使うので、上限の無い接続はメモリを使い切る

## 14. 負荷と応答時間の試算

平均 10 秒で 1 区切りを処理し、入力 8 KB、訳 3 KB、途中の断片を 200 ms ごとに POST すると仮定する。
翻訳のデータは、仲介の受信と送信を合わせて 1 区切りあたり 22 KB。

| 同時の翻訳 | 割り当て (毎秒) | 結果の POST (毎秒の目安) | 翻訳のデータの帯域 |
| ---: | ---: | ---: | ---: |
| 10 | 1 | 50 | 約 0.18 Mbps |
| 100 | 10 | 500 | 約 1.8 Mbps |
| 1,000 | 100 | 5,000 | 約 18 Mbps |

HTTP のヘッダー、TLS、SSE の書式、生存の確認は別にかかる。翻訳中 100 件、待機中のワーカー 200 台、利用者の
順番待ちなしなら、長く開く要求は約 300 本。25 秒のロングポーリングなら、待機中のワーカーによる更新は平均で毎秒 8 回。
確認用ジョブと抜き取りは、運営のエンジンに全体の 7% ほど (暫定の率の合計) の負荷を足す。

ワーカーが待機中なら、ポーリングの更新を待たずに割り当てられる。推論の速さが同じで、ワーカーとの往復が
40〜100 ms なら、空きがあるときに足される遅れは、その往復と仲介の処理が中心になる。無作為に選ぶので、
速いワーカーを優先する構成より平均は遅くなる。分散のための代償として受け入れる。

- 利用の規約: 他人の個人情報、業務上の秘密、認証に使う情報を入れないこと。責任の範囲
- 参加の規約: 8.1 の内容。違反したときの失効

  公式の枠を出すなら、受け取る相手 (運営、CDN、参加者)、残すもの、期間を書き直す

  拡張の画面の両方に目立つ形で書く。[Limited Use](https://developer.chrome.com/docs/webstore/program-policies/limited-use) は、
  人が利用者のデータを読めるのは、特定のデータについて利用者の明示の同意があるときなどに限っている。
  4 章の同意がこれを満たすかは、審査に出す前に確かめる
- 個人情報の保護の法律: 利用者の同意は、ページに写るほかの人の個人情報には及ばない。事業者が顧客の情報を送る使い方は

- 著作権: 第三者の端末で他人の著作物を訳す構成の扱いを確かめる
- 記録を持たない運用 (12 章) で足りるか。調べた範囲では、この種のサービスに記録の保存を義務付ける決まりは
  見当たらないが、専門家に確かめる

## 17. 実装の順と受け入れの条件

試験は `tools/mock_plamo.py` と、足すワーカーのモックを相手にする。本物のエンジンと本番にはつながない。

### 17.1 順

1. **直結プール:** 複数のエンジン、待ち行列、用途と層の順番。既存の API と設定がそのまま動くこと
2. **匿名の層:** 資格の発行 (保存なし)、Cookie、層ごとの上限、国の確認
3. **ワーカーの接続:** 登録、ポーリング、結果、停止、期限、割り当て直し、分散
4. **改ざんの検出:** 確認用ジョブ、抜き取り、検査、試用と検疫
5. **デスクトップからの参加:** エージェント、設定の画面、電源と自分の翻訳の優先
6. **クライアントの同意と表示:** Web、デスクトップ、拡張

ボランティア枠を公開できるのは、1〜6 と 15 章が済んでから。

第1・第2段階のサーバーAPIは実装済み。層の重み、匿名の枠、発行・送信量・国の制限を適用する。
資格は保存せず、IPのまとまり・資格の乱数・文字数・件数をメモリで集計する。
文字数集計は層ごとに10,000キーまでとし、ほかの各集計も10,000キーまでとする。
満杯ならその集計の新しいキーを503で断り、生きた制限を消さない。
秒単位でまとめるため、時間窓の期限は最大1秒長くなる。期限切れは次の集計時に削除する。
Cookie用のOriginは `TR_PUBLIC_SERVER_URL` と比較し、未設定ではCookieの発行・認証を断る。
匿名ログインの画面とワーカー以降は未実装で、ボランティア枠は起動できない。
実装済みの設定・API・待機数の上限は SPEC 5 章を参照。

## 18. 決めたことと、まだ決めていないこと

### 18.1 決めたこと (2026-11-11)

| # | 決定 | 理由と、受け入れた危険 |
| --- | --- | --- |
| 1 | ボランティア枠は、同意すればページ翻訳を含むすべての翻訳を受ける | 使い勝手を優先する。ログイン後のページや他人の個人情報が参加者に渡り得る。4 章の同意と表示、15 章の確認で補う |
| 2 | 改ざんの検出は、確認用ジョブと抜き取りの再実行 | 狙った改ざんも確率的に見つかる。運営のエンジンの余力が要る。見つかるのは配信の後 |
| 3 | 仲介は原文を読める。公開入口に CDN を置く | 入力の検証と改ざんの検出を仲介で行える。DDoS に強い。CDN の事業者も読める立場になる |
| 4 | 利用者の参加は制限しない。匿名と登録済みで優先を変える | 登録なしで試せる。乱用は匿名の層に閉じ込める。匿名の層の制限は資格に頼れないので、枠と IP で縛る |
| 5 | 匿名の層も全機能を使える | ページ翻訳は量が多く、匿名の層が埋まりやすい。7.2 の順番と 5.4 の上限で抑える |
| 6 | ボランティア枠でも `history` を常に渡す | 訳の質を運営管理枠と同じに保つ。各ワーカーが 2 区切り分を読め、前の訳が要る区切りは順にしか流せない |
| 7 | 計算の提供は、アカウントの登録と規約の同意が要る | 1 人あたりの端末数を縛れ、失効が効く。参加の敷居は上がる |
| 8 | 計算の提供量による優先は v1 に入れない | 貢献の水増しという攻撃の面を作らない |
| 9 | 割り当ては区切りごとに無作為に、所有者をまたいで分散する | 1 人に内容が集まらない。漏れる量の期待値は変わらず、断片を読む人の数は増える。平均の応答は遅くなる |
| 10 | アカウントの登録に要るのは、確認の済んだメールアドレスだけ。持つのは IdP だけ | 個人情報を持たない。1 人が複数のアカウントを作れるので、所有者ごとの上限は防ぎ切れない |
| 11 | 提供は日本の中に限る (利用者も参加者も) | 越境の移転と GDPR の論点を避ける。VPN で国を偽ることは防げない |
| 12 | 誤訳の報告は受け付けない | ジョブとワーカーの対応を残さずに済む。利用者が気づいた改ざんを検出に生かせない |
| 13 | 所有者が少ない時期も、ページ翻訳を受ける | 始めから全機能を出せる。少数の参加者が多くを読める |
| 14 | 仲介は極力何も持たない。匿名の資格は保存せず、成績はメモリだけ、ジョブごとのログは書かない | 漏れるものが無い。乱用や漏えいを後から調べられない。匿名の資格を 1 つずつ失効できない |
| 15 | CDN は Cloudflare | DDoS と IP 単位の制限を任せられる。外国の事業者が内容を読める立場になり、CDN の側のログは仲介から消せない |
| 16 | 資格の発行に計算の課題 (proof of work) は付けない | 弱い端末と電池に響かない。資格の大量の取得は、Cloudflare の制限と匿名の層の枠の上限だけで抑える |
| 17 | 使い捨てのメールアドレスは IdP で断る | 複数のアカウントを作る手間が上がる。ドメインの一覧の保守が要り、漏れは残る |
| 18 | 集計のログは 30 日。Cloudflare の設定は 13 章の表 | 障害と混雑を調べるのに足りる最短の期間にした。Cloudflare の側のログは別 |

### 18.2 実装の都合で決めたこと (異論があれば変える)

- サーバーは標準ライブラリだけなので、ワーカーの資格は乱数とハッシュ、匿名の資格は HMAC の署名にした。公開鍵の署名は使わない
- エージェントには検証済みの入力を渡し、プロンプトはエージェントが組む。仲介が組んだ文字列は渡さない
- 運営管理枠とボランティア枠は、仲介を分ける (1 つの仲介に 1 つのプール)
- ワーカーの自動の失効はしない。検疫までを自動にし、失効は運営が決める
- 規約の同意の記録 (所有者の名前、版、日) は、決定 14 の例外として残す

| --- | --- |
