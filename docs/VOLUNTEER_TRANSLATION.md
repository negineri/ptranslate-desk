# 翻訳ワーカーのプールとボランティア運用（v1 設計案）

この文書は検討中の案。現行の公開 API と動作は [SPEC](SPEC.md) を参照。v1 では閉域内のプールを先に実装し、同じ仕組みの上で公式のボランティア枠を試す。

## 構成とデータの扱い

Web、デスクトップ、ブラウザ拡張は、選択した一つの翻訳サーバーへ接続する。翻訳サーバーが認証、入力検証、待ち行列、ワーカーへの割り当て、訳の中継を担当する。

- 個人運用では、既存の単一エンジンを一枠のプールとして使える。複数台構成では、サーバーから管理下のエンジンに閉域内で直接接続する。
- 公式の運営管理枠とボランティア枠は、接続先、ワーカー資格、割り当て先を分離する。混雑や停止による自動切り替えは同じプール内に限る。
- ボランティアの端末では原文、文脈、用語集、直前の原文と訳を読める前提とする。枠は初期状態で無効とし、最初の自動送信より前に、第三者に渡る内容を示して利用者が選ぶ。認証情報とアカウント情報はワーカーへ渡さない。
- 翻訳内容や認証情報は、ワーカー、仲介、公開入口のログに残さない。上流のエラー本文もログに出さない。クライアントの認証情報と訳キャッシュは接続先ごとに分ける。

## 利用者の接続と認証

既存の HTTPS の `POST /api/translate` と SSE を使い、1 区切りを 1 リクエストとする。認証・入力検証・同時実行枠の確認後に受け付け、待機中は SSE の `: ping`、実行中は訳の断片を返す。待機期限を超えたら SSE のエラーで終える。公開入口の HTTP/2 で単文とページのストリームを並行して流せるようにする。利用者が接続を閉じたら、待機中の仕事を除去し、実行中なら割り当てを取り消す。

公式は氏名やメールアドレスの登録なしで、インストールごとにランダムな匿名の利用資格を発行する。初期公開では招待コードで発行数を絞る。サーバーに持つのは資格情報のハッシュ、有効期限、失効状態、制限に必要な利用量のカウンターとする。デスクトップと拡張は短命の Bearer トークンを使い、同じサーバーから配信する Web 画面では HttpOnly Cookie を使う。個人運用では既存の OIDC や閉域の認証を選べる。

資格の取り直しを前提に、発行時の短時間の IP 単位の制限と、サービス全体の同時実行数・待ち行列の上限を設ける。IP は恒久的な利用者 ID に使わない。公開入口や CDN も含め、ログの項目と保持期間は公開前に決める。

## ワーカーの接続

参加者のマシンでエージェントが公式の仲介へ外向き HTTPS 接続を開始する。推論エンジンは参加者のマシンの localhost に置ける。ワーカーは利用者向けの資格と分けて招待登録し、個別に失効できる資格で接続する。

1. 空き枠があるエージェントがロングポーリングし、仲介は仕事が入った時点で期限付きの割り当て ID と翻訳入力を返す。
2. エージェントは訳の断片を短い POST で返す。断片に連番を付け、再送を重複表示しない。最初と最後の断片および終了通知は即送信し、途中の断片はまとめて送る。
3. 仲介は割り当てをワーカー資格にひも付け、失効後の結果を破棄する。結果 POST または定期的な生存確認の応答で停止を伝え、ワーカーは推論接続を閉じる。
4. ワーカーの離脱時は、利用者に最初の断片を返す前に限り、同じプール内で一度だけ再割り当てする。断片を返した後や、再割り当てにも失敗した場合は SSE のエラーで終える。正常終了を示す通知なしの上流切断は失敗として扱う。

## 単文とページの割り当て

ワーカーは共有し、優先度と同時実行数を用途ごとに制御する。用途は API の任意フィールドで受け取り、未指定の呼び出しは従来どおり受け付ける。ページの仕事にはグループ ID を添える。

| 用途 | 割り当て |
| --- | --- |
| 対話 | デスクトップや拡張で選択した一文など。次の空き枠を優先する |
| ページの表示範囲 | 画面内の段落を先に送り、スクロール後は新しく見えた範囲を優先する |
| ページの残り | 空き容量で処理し、待ち時間に応じて割り当て機会を与える |

同じ優先度では利用者を順番に回す。利用者ごとの上限が 2 本なら、ページは複数タブの合計でまず 1 本に抑える。クライアントの優先度申告はヒントとして扱い、利用者単位の上限を適用する。複数枠のあるプールではページが全枠を埋めないようにする。1 枠のときはページの区切りを短くし、実行中の区切りが終わってから対話に枠を渡す。

拡張はページ全体を一度に仲介へ送らず、区切りが終わるたびに次を送る。前の訳が必要な区切りは `history` を使って順に処理する。遷移や停止で、待機・実行中の翻訳リクエストを閉じる。

## 負荷と応答時間の試算

平均 10 秒で 1 区切りを処理し、入力 8 KB、訳 3 KB、途中の断片を 200 ms ごとに POST すると仮定する。翻訳データは仲介の受信と送信を合わせて 1 区切りあたり 22 KB。

| 同時翻訳 | 割り当て毎秒 | 結果 POST 毎秒の目安 | 翻訳データの帯域 |
| ---: | ---: | ---: | ---: |
| 10 | 1 | 50 | 約 0.18 Mbps |
| 100 | 10 | 500 | 約 1.8 Mbps |
| 1,000 | 100 | 5,000 | 約 18 Mbps |

HTTP ヘッダー、TLS、SSE の書式、生存確認は別途かかる。HTTPS 接続を再利用する。翻訳中 100 件、待機ワーカー 200 台、利用者の順番待ちなしなら、長く開くリクエストは約 300 本。25 秒のロングポーリングなら、待機ワーカーによる更新は平均毎秒 8 回。現行の `ThreadingHTTPServer` では開いたリクエストごとにスレッドを使うため、帯域に加えて CPU、メモリ、同時接続数を測る。

ワーカーが待機中ならポーリングの更新を待たずに割り当てられる。推論性能が同等でワーカーとの往復が 40〜100 ms なら、空き枠があるときの追加遅延はその往復と仲介処理が中心になる。最初の断片は即送信する。混雑時は待ち時間とワーカーの推論性能も分けて測る。

## デスクトップからの参加

デスクトップの設定に初期状態でオフの「翻訳の処理を提供する」を置き、ワーカーは別プロセスとして動かす。招待コードで登録し、対応モデルと試験翻訳を確認して参加する。待機中・処理中・一時停止を表示し、登録解除でワーカー資格を失効させる。アプリ起動中に 1 枠を提供し、バッテリー駆動中は新規の仕事を受けない案から始める。

自分のローカル翻訳を既定で優先する。同じ推論エンジンを使う場合は、新規の割り当てを止め、実行中の区切りの終了後に枠を返す。提供する仕事の実行時間を制限し、自分の単文翻訳への影響を測る。翻訳の接続先と計算枠の提供先は別々に選べる。

## 実装順と確認項目

1. 閉域内の複数エンジンを束ね、既存 API と単一接続先の設定を使えるようにする。待ち行列の上限、切断時の枠の回収、終了通知のない切断をモックで確認する。
2. 招待制のワーカー接続と公式の匿名利用枠を追加する。停止通知、連番の再送、割り当て期限、プール間の分離をモックで確認する。合成の確認用ジョブで異常なワーカーを検出する。
3. 同じモックを直結と仲介経由で比較する。空き枠があるときの最初の断片は直結比で p95 の増分 200 ms 以内を暫定目標とする。混雑時は単文の初回表示、ページの表示範囲の完了、待機時間の p50/p95 を測る。
4. デスクトップからの参加を試し、自分の翻訳への影響、電源状態の変化、アプリ終了時の挙動を確認する。

公開前に決めるのは、招待の配り方、利用量と待機時間の上限、低優先度への枠の配分、モデルの対応条件、ログの保持期間、ワーカー停止通知の目標時間。API の用途や第三者への送信範囲を確定したら [SPEC](SPEC.md) に反映する。
