# 訳の繰り返しと揺れの調査（2026-11-07）

同時に2本以上流すと訳が同じ文を上限まで書き続ける（`finish: "length"`）ことがある、という観察から始めた調査の記録です。
llama.cppの高速化（並列処理、Flash Attentionなど）が原因かを確かめました。

## 結論

- 繰り返しは、**計測用に作った人工的な原文**（段落の繰り返しがあり、しかも単語の途中で切れている）でだけ起きた。
  画面が送る形の原文や普通の文章では、どのエンジンでも一度も起きなかった（300本以上）
- 並列処理そのものは原因ではない。temperature 0の貪欲法は、この原文では止まるか周回するかの境目にあり、
  同時に処理する本数などによる小さな数値の差でどちらに倒れるかが変わる
- Strix Halo（Radeon 8060S）のVulkanでは、これとは別に、**前のリクエストの状態で訳が変わる揺れ**がある
  （masked-V leak）。上流のllama.cppにはまだ修正が無く、halo-box/strix-llama.cppで直っている
- 対策として試した `frequency_penalty` は、段落単位の長い周期の繰り返しを防げず、普通の訳もわずかに変えるので採用しなかった

## 環境

| 項目 | 値 |
| --- | --- |
| モデル | PLaMo 3 Translate 2B、Q4_K_M（`n_swa = 2048` のsliding window attentionを持つ） |
| エンジン | llama.cpp b11804（`-c 65536 -np 4 -fa on`）、比較にhalo-box/strix-llama.cpp b1046 |
| GPU | Ryzen AI Max+ 395 / Radeon 8060S（gfx1151、RADV、Vulkan） |
| CPU | 同じ機械のCPU（16スレッド）と、Proxmox上の4 vCPUのVM（CPU種別EPYC-Rome-v4） |
| 要求 | PTranslateと同じPFML3のプロンプト、`temperature: 0`、`cache_prompt: false` |

同じ原文を何度も流し、訳のハッシュを比べて「同じ訳か」を、`finish: "length"` で「繰り返したか」を数えました。

## 1. 同じ入力でも訳が変わる（Radeon 8060SのVulkan）

枠を1つ（`-np 1`）にして1本ずつ流しても、前のリクエストが残した状態で次の訳が変わりました。

| 設定（1本ずつ5回） | 結果 |
| --- | --- |
| GPU、`-fa on` | 2種類の訳が交互に出る。起動し直した直後の1本目だけは毎回同じ |
| GPU、`-fa on --swa-full` | 1回目だけ違い、あとは同じ |
| GPU、`-fa off` | 5回とも同じ |
| GPU、`GGML_VK_DISABLE_COOPMAT=1` | 5回とも同じ（ただし約2倍遅い） |
| CPU | 5回とも同じ。起動し直しても同じ |
| GPU、halo-box b1046 | 5回とも同じ。起動し直しても同じ |

原因は[llama.cpp #26744](https://github.com/ggml-org/llama.cpp/issues/26744)と同じものです。
Flash Attentionで完全にマスクされた列はP = +0.0ですが、P × VはVの符号を受け継ぎます。解放済みのKVセルに残った値から-0.0が入り、
gfx11のWMMAは-0.0を正確に足さないため、出力が前のリクエストに引きずられます（約1 ulp）。
#26744は「ドライバー側の問題」として直されないまま閉じられています。
修正は[strix-halo-llamacpp](https://github.com/Nathanw1014/strix-halo-llamacpp)のv0.7.4で、解放したKVセルを0で埋める形で入りました
（commit `ea35c5066`）。その後継の[halo-box/strix-llama.cpp](https://github.com/halo-box/strix-llama.cpp)にも入っています。
strix-halo-llamacppのv0.8.0は、PLaMo 3のトークナイザー（`plamo3`）に対応しておらず、このモデルを読めませんでした。

halo-box b1046は、上流と速さが同等でした（生成は同等、原文の読み込みは2,929から3,513トークン/秒）。

## 2. 同時に処理する本数で訳が変わる（CPUでも）

CPUは決定的で、同じ本数なら何度流しても同じ訳でした。それでも1本、2本、4本で訳が変わります。
まとめて計算するときの数値の差によるもので、llama.cppでは仕様の範囲です。訳はどれも言い換え程度の違いでした。

## 3. 繰り返しの引き金

計測に使っていた原文は、英語の3段落A、B、Cを「A B C A B C」と並べ、1,500文字で機械的に切ったものでした
（末尾は「…reverted by the n」と単語の途中）。CPUで4本同時に流すと、毎回繰り返しました。
繰り返した訳は3段落分（約460文字）の周期で、原文の切れ目を越えて周回を続けていました。

| 原文（CPU、上流b11804） | 1本 | 4本同時 |
| --- | --- | --- |
| 繰り返しあり、単語の途中で切れる（計測に使っていた原文） | 0/2 | 8/8 |
| 画面が送る形（A B C A、段落の終わりで切れる） | 0/2 | 0/8 |
| 繰り返しあり、切らない（A B C A B C） | 0/2 | 0/8 |
| 繰り返しなし、単語の途中で切れる | 0/2 | 0/8 |
| 同じ段落を2回貼っただけ（A A） | 0/2 | 0/8 |

2つの条件がそろったときだけ起きました。画面は空行と文の終わりで区切って送る（[SPEC 4.1](SPEC.md)）ので、
単語の途中で切れるのは、文の終わりが無いまま1,500文字を超える段落だけです。通常の使い方ではまず起きません。
起きても、訳の長さは原文の1.5倍で止まり、画面に「切れた」と出ます。

`tools/bench.py` の原文は、この調査の後、同じ文を繰り返さないものに替えました。

## 試して採用しなかった対策

繰り返しのある原文（上の1行目）で試した結果です。

| 対策 | 結果 |
| --- | --- |
| `-fa off`、`--swa-full`、`-kvu`、`--no-cont-batching` | 揺れも繰り返しも残った |
| `GGML_VK_DISABLE_COOPMAT=1` | 揺れは消えたが約2倍遅く、繰り返しは残った |
| `dry_multiplier: 0.8` | 10回中3回繰り返した |
| `repeat_penalty: 1.1` | 繰り返しは消えたが、言い回しがやや不自然になった |
| `frequency_penalty: 0.3` | GPUで20回中6回繰り返した（無しで10回） |
| `frequency_penalty: 0.5` | GPUでは20回中0回。CPUで4本同時だと16回中16回繰り返した |

llama-serverの `frequency_penalty` と `repeat_penalty` は、直近64トークン（`repeat_last_n` の既定）しか見ません。
段落単位（200トークン以上）の周期はこの窓に入らないので防げません。普通の原文の訳は0.5でも言い換え程度しか変わりませんでしたが、
ほぼ起きない条件のために全員の訳を変える理由は無いと判断し、入れませんでした。

## 確かめていないこと

- NVIDIA、Intel、Apple Silicon（Metal）のGPU
- CPUはx86の2種類だけ
- halo-boxのCPUでの繰り返し（GPUでは、繰り返しのある原文を1本と4本同時で計20回流して0回）
